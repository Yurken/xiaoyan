# Grok 4.6 Android 主程评测

- 日期：2026-09-12
- 状态：已完成；采纳 Android 端代码与构建升级，继续采用“Grok 窄任务主程 + Codex 架构与验收”的协作方式
- 分支：`codex/grok-060-next`，本轮 SDK 54 收尾基于 `9cd8ce64580c6acd8c0935cfee6b0f3183ab2406`
- 候选工具：Grok Build CLI `1.0.13`（构建 `5e9a58528b76`）
- 候选模型：`grok-4.6-build`
- 运行方式：独立凭据目录、禁用子代理与联网搜索；Grok 负责受约束实现，Codex 负责架构边界、故障复现、依赖核对、原生构建和模拟器验收
- 对照：0.6.0 分支中只能作为 Expo 开发壳运行、没有真实连接与发布验证的 Android 端

## 主假设

如果把 Android 0.6.0 切成可独立验收的短任务，并由 Codex 固定架构边界、复现故障和执行发布级原生验收，那么 Grok 4.6 可以作为主程补齐后端连接、账号、通知、远程数据、离线降级与 Android 发布链路，且不破坏桌面端和核心 Agent 门禁。

杀停标准为：继续把副作用堆进页面、伪造推送或离线能力、只通过 JS 检查却无法生成并启动 APK、降低 Android 发布兼容性，或核心 Agent 门禁退化。

## 实现结果

- 后端连接支持模拟器默认地址、真机局域网地址、严格 URL 归一化和保存后探测。
- 账号支持注册、登录、退出与 SecureStore 会话持久化；需要认证的请求统一使用会话令牌。
- 论文库、工作台与聊天采用远程优先，并在后端不可用时读取 WebDAV 同步副本；界面明确标记只读与不可用状态。
- React Native 端补齐 SSE 流解析与测试；通知入口只承诺已经实现的本地测试通知，远程任务完成提醒明确依赖后端推送服务。
- 页面中的远程调用、持久化与状态机已拆入 hooks/features，设置、知识库等页面保持组合职责。
- EAS 配置和 GitHub Actions 校验 `EXPO_TOKEN`、`EXPO_PROJECT_ID` 与构建 profile；缺少云端密钥时明确失败，不伪造可发布状态。
- 从 Expo SDK 52 / React Native 0.76 升级到 Expo SDK 54 / React Native 0.81.5，启用 Hermes、新架构、API 36 与 16 KB 页面支持；Worklets 固定为 SDK 54 推荐的 0.5.1，Babel 使用 `react-native-worklets/plugin`。
- Metro 只对 React 与 React Native 做移动端定向解析，避免 monorepo 中桌面 React 版本进入移动 bundle，同时保留其他依赖的正常层级解析。

## 故障发现与修复证据

第一次 SDK 52 原生烟测发现三个仅靠 TypeScript/Expo 导出无法发现的问题：JSC bundle 报 `Unexpected EOF`、monorepo 同时打入 React 18/19、API 37 的 16 KB 模拟器显示兼容模式警告。Grok 在 Codex 给出单一故障与文件边界后分别完成 Hermes、Metro 定向解析和依赖升级修复。

SDK 54 原生构建又暴露 Worklets/Reanimated 链接错误。Grok 第一轮判断为 Gradle 并行竞态，关闭并行后错误仍可复现；第二轮根据 Expo 自带版本表将 Worklets 从 pnpm 自动解析的 0.8.3 固定到 0.5.1，并更新 Babel 插件。最终剩余错误来自本次隔离工作树位于 macOS 临时目录及 Gradle 自动链接缓存中的旧绝对路径。Codex 将工作树移出临时目录、重启 daemon 并清除生成清单后，四个 ABI 的原生构建全部通过。项目源码未加入针对本机临时路径的补丁，也未修改 `node_modules`。

## 验证结果

- Mobile：2 个测试文件、19 项测试通过；type-check、lint、Expo 依赖检查通过。
- API SDK：6 项 SSE 流测试通过。
- Android 原生：Gradle `assembleDebug` 成功，420 个任务中 355 个执行、65 个复用；compile/target SDK 36、NDK 27.1、Hermes、新架构与四 ABI 均完成构建。
- APK：175,300,675 bytes，SHA-256 `e556001783fa92093864e813e29a3ca1abf132978d3ace47a6970077124be900`。
- 16 KB：Build Tools 36 `zipalign -c -P 16 -v 4` 通过；APK 内 arm64-v8a 与 x86_64 共 40 个共享库的全部 ELF `LOAD` 段至少为 `0x4000` 对齐。
- 生产清单：min SDK 24、target SDK 36；未合入读写外部存储、悬浮窗或生产明文网络配置。
- 模拟器：在 API 37、页大小 16384 的 `sdk_gphone16k_arm64` 上全新卸载再安装；论文库和设置页正常渲染，没有兼容性警告、崩溃、JavaScript 异常或 Worklets 错误。
- 核心 Agent：评分器 8 项测试通过；E01/E02/E06/E08 候选均分 2.5、硬失败 0、未知硬失败 0，成对非退化门禁通过。本轮没有把 Android 开发结果伪装成开放式模型质量提升。

云端 EAS 构建仍需要仓库环境配置真实 `EXPO_TOKEN` 与 `EXPO_PROJECT_ID`；远程聊天、论文与账号的完整联调仍需要启动兼容的 0.6.0 后端。二者属于部署环境前置条件，移动端已提供可见错误与离线降级。

## 能力差异与决策

Grok 在页面拆分、连接/账号闭环、SSE 兼容、构建配置和针对单一报错的修复上产生了可验收代码，属于本切片提升。它对宽范围任务仍容易达到最大回合；一次原生故障根因判断也需要 Codex 反证后修正。原生构建、依赖兼容、临时路径问题和 16 KB 发布验收仍依赖架构师主动检查。

采纳本轮 Android 端实现与 SDK 54 升级。后续允许 Grok 在明确输入、文件范围和单一验收目标下继续担任 Android 主程；Codex 保留架构、依赖、原生发布与设备验收责任。暂不把 Grok 设为无需复核的仓库默认主程，也不因这次编码成功修改小妍产品内的默认 Agent 模型。
