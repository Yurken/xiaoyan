## 问题证据

原 import_all_data 完成插入后先 tx.commit，再通过 pool 执行 load_all_settings。若提交后读取失败，命令返回 Err，但数据库已经恢复，内存设置缓存仍是旧值。

settings_get → get_exposed_settings 只读取内存 cache，补默认值并脱敏，不重新查询数据库。因此这时再次 settings.get 成功也可能拿到旧配置，不能作为恢复结果的权威判定。

以上是现有源码控制流证据，不是运行复现。

## 实现策略

将本次触达的事务提交/缓存发布逻辑从大 settings_service 提取为 settings_backup_commit::commit_restored_settings：

1. 使用同一个 `&mut *tx` 连接读取最终 settings 行，不另从 pool 借连接；可看到本事务恢复后的值，也不会在单连接池中等待自己的连接。
2. 在提交前构建完整的新缓存：默认值合并所有数据库原始行。保留未知键、敏感原值与空字符串，不使用脱敏或 exposed-key 过滤。
3. 读取并构建缓存后提交事务；只有提交返回成功才取得缓存写锁并整份替换。
4. 提交成功后不再执行可返回 Err 的数据库查询；返回成功前完成缓存替换。

commands/data_backup 与仍注册的 WebDAV 整包备份恢复都通过 import_all_data 获得这一行为。备份格式、加密协议、表范围、文件恢复方式和前端 API 返回类型没有变化。
