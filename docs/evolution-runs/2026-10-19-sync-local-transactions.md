# 增量同步的本地事务边界（2026-10-19）

## 问题
同步原先在事务外读取所有本地时间戳，然后把远端合并计划写入数据库。本地记录若在这两个步骤之间从 t1 更新到 t3，远端 t2（t1 < t2 < t3）仍可能覆盖它；远端删除也有相同窗口。

删除检测与末尾基线刷新同样分离：开始检测时记录仍存在，网络等待期间用户删除，末尾直接把空集合记成新基线，下一次同步便无法发现这次删除。此外，合并行只比较本次远端墓碑，没有比较数据库已保存的本地墓碑，旧远端行可能恢复已删除的本地记录。

## 实现
- 从 sync_service 提取 sync_local_state，统一持有数据库事务。使用 SQLx Pool::begin_with("BEGIN IMMEDIATE") 在读取基线或行时间戳之前取得写事务；网络、附件读取/哈希、序列化及加密不在事务内。
- capture_local_state 在同一事务里检测删除、保存墓碑、推进本地基线并读取全部同步表和墓碑。逐行转换并立即排除设备专属设置和重列，不再保留整表 SqliteRow 数组或再克隆完整 JSON 行。原备份读取模块保持不变。
- 基线表示最近一次原子完成的本地观测，不表示上传已确认。上传失败后墓碑仍持久保存；后续捕获会带上它们，已观测记录的后续删除也仍能被发现。
- apply_merge 在同一写事务内再次检测网络期间发生的删除，把本地与远端墓碑按现有时间比较规则取新；删除与 upsert 前读取当前行时间戳。远端行必须严格新于现存行及有效墓碑才会写入，行与墓碑同时间时删除胜出。
- 合并后的基线与业务变更一起提交，不再在事务外刷新。没有远端快照时也通过 checkpoint_local_deletes 原子检测删除并推进基线。合并失败时，本次业务变更、墓碑和基线一并回滚。
- 对同一次删除的重复观测不修改其时间；记录重新出现并被基线观测后再次删除，可以推进已有旧墓碑。损坏的基线 JSON 返回错误，不再当作空基线静默覆盖。
- 对未知表的墓碑继续保存和透传，但仅允许固定 BACKUP_TABLES 的表名进入本地查询，保留旧版时间戳表映射隐含的限制。
- 原 SQL upsert 与资产引用恢复逻辑提取到 sync_merge_row。协议版本、RCSYN1、表范围、时间戳格式兼容和记录级 LWW 规则保持不变。

依据：[SQLite BEGIN IMMEDIATE 与事务隔离](https://www.sqlite.org/lang_transaction.html)、[SQLite WAL 隔离](https://www.sqlite.org/isolation.html)、[SQLx 0.8.6 Pool::begin_with](https://docs.rs/sqlx/0.8.6/sqlx/struct.Pool.html#method.begin_with)、[SQLx 事务析构与提交](https://docs.rs/sqlx/0.8.6/sqlx/struct.Transaction.html)。以上是源码设计与 API 文档依据，未通过原生编译验证。

## 范围与资源
写事务覆盖本地数据捕获或合并，因此其它数据库写入可能等待；没有把网络延迟或附件哈希时间加入持锁区间。大库读取仍可能较长，未做时延和内存实测。全部同步 JSON、加密内容与附件仍有内存开销，本轮没有实现流式加密或附件分块。

删除时间仍是观察到缺失的时间；首次建立基线之前、或两次观测之间完成创建再删除的未观测记录，不会生成新墓碑。设备时钟偏差、相同时间戳的行冲突、附件与数据库的跨资源一致性、远端协议校验和同步后设置缓存刷新属于既有边界，本切片不宣称解决这些问题。网络等待期间产生的墓碑在本地保留，通常由下一轮出站快照传播。
