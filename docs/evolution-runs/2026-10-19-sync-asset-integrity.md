# 增量同步附件的失败处理与内容校验（2026-10-19）

## 问题
出站快照原先用 Option 吞掉源文件读取错误；上传阶段再次读取失败又直接 continue。结果可能发布设备私有绝对路径，或发布尚未上传的 asset:// 引用。入站附件 404 会留下空 mapping，upsert 再用 unwrap_or_default 将既有有效 file_path 覆盖为空。已有缓存仅按 exists 判断，下载明文也没有核对内容哈希。

## 改动
- 从 sync_service 提取 sync_assets；数据库捕获后才执行附件准备。非空源路径读不到或仍是未解析的 asset:// 时返回错误，不发布该快照。
- 源文件和缓存校验使用 64 KiB 固定缓冲区逐段 SHA-256，复用同一源路径的哈希结果。待上传文件重新读取后核对快照哈希；文件消失或改变时在上传该文件和发布状态文件之前报错。已上传的早先附件可能保留，状态文件不会继续发布。
- 下载器仅收集三个附件表的引用，并跳过远端墓碑已经淘汰的行。每个哈希保存成功路径或具体错误，只有事务内最终胜出的远端行才要求可用 mapping；被较新本地行或本地墓碑淘汰的旧行不因附件失败阻断同步。
- 有效缓存先核对明文 SHA，命中后不请求远端。损坏/不可读缓存尝试重新获取；404、下载/解密错误或明文哈希不匹配都不会进入成功 mapping，也不会清空已有记录路径。
- 校验通过的明文写入同目录独占创建的随机临时文件，完整写入、sync_all、关闭后 rename；失败只清理本次临时文件，不先删除旧缓存。仅成功安装后返回本地路径。
- 哈希必须是现有生成格式的 64 位小写十六进制；扩展名允许空值、安全的大写和 Unicode，但拒绝分隔符、控制符、Windows 非法字符及结尾点/空格。缺少扩展元数据继续用空扩展名，不把外部字符串变成目录。
- 选中行的附件 mapping 缺失、为空或携带错误时，upsert 返回错误，整笔本地合并的业务数据、墓碑和基线一起回滚。显式 NULL/空 file_path 及没有此字段的行保留原语义。

文件安装依据：[Rust rename](https://doc.rust-lang.org/std/fs/fn.rename.html)、[OpenOptions::create_new](https://doc.rust-lang.org/std/fs/struct.OpenOptions.html#method.create_new)。这是源码设计依据；未实测文件系统行为、崩溃恢复或原生编译结果。

## 兼容边界
RCSYN1、状态版本、远端 assets/{hash}.rcblob、本地 sync_assets/{hash}{ext}、记录级胜负规则均保持。旧版可能写出的非空远端绝对路径不再覆盖本地文件路径：若该行实际胜出则显式报错，需要源设备在附件可读时重新同步生成有效引用；旧行已被淘汰则不阻塞。这是对既有坏快照的处理变化，不声称旧坏数据无需修复即可同步。

文件准备失败前的本地观测基线和墓碑已由上一阶段提交，仍保留待下次同步。下载阶段已验证的缓存文件可能在后续数据库合并失败后保留，供重试复用；没有跨 WebDAV、文件系统与 SQLite 的分布式事务。合并时不在 SQL 事务内再次读文件，其他进程在校验后移除/改变文件仍是边界。

现有远端目录命中优化保留：同名 blob 存在时不重新下载验证或覆盖上传，因此不会自动修复远端已经损坏的 blob。缓存仍按哈希加扩展名定位，扩展提示改变可能再次下载。上传、下载、加密和完整快照仍需要完整缓冲区；64 KiB 只描述哈希阶段，不代表总内存限制或实测内存下降。
