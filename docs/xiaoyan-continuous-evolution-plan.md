# 小妍持续进化规划

> 文档性质：长期维护的产品与工程总纲
>
> 当前版本：`0.1.0`
>
> 建立日期：2026-07-29
>
> 最近更新：2026-07-29
>
> 下次强制更新：Codex 开发模型升级、核心 Agent 架构变化或小妍正式版本发布前
>
> 适用范围：以 Desktop 为旗舰端，选择性同步 Web / Mobile

## 1. 这份文档解决什么问题

小妍的长期目标不是不断增加功能入口，而是让同一个用户在持续使用后，明显感受到：

- 小妍越来越理解他的研究主题、目标、习惯与约束；
- 上次做到哪里、为什么这样决定、下一步做什么，都能自然续接；
- 相同错误更少重复发生，用户纠正过的内容能在授权范围内被正确复用；
- 回答、建议和执行结果更可信、更可追溯，也更容易恢复；
- 每次 Codex 开发模型能力升级，都能转化为小妍真实、可验证的产品改进。

本文是“活文档”，同时承担四个职责：

1. 定义小妍“越用越好用”的产品含义和边界；
2. 管理跨版本的优先级、指标、风险和技术演进；
3. 规定 Codex 升级后必须执行的评测与代码迭代流程；
4. 保存每轮决策及结果，避免规划与代码脱节。

本文不替代单功能 PRD。具体功能仍应有独立设计文档；本文负责回答“为什么做、先做什么、如何判断真的变好”。

## 2. 核心原则

### 2.1 先提高连续研究质量，再增加功能数量

优先解决上下文断裂、重复输入、来源不清、执行不可恢复和用户纠正不生效。新入口数量、对话次数和 Token 消耗不作为“更好用”的直接证据。

### 2.2 记住有价值的信息，不是记住一切

长期记忆只保存对未来任务确有帮助的结构化信息，例如研究目标、明确偏好、关键决策、开放问题和下一步行动。原始对话、论文正文、截图和敏感数据不因“个性化”被默认永久保存。

### 2.3 先证据，后结论

涉及论文、实验、知识主张和投稿判断时，结果应尽量关联本地论文、知识节点、实验记录或可靠外部来源。无法确认时明确说明不确定性，不用流畅表达掩盖证据缺口。

### 2.4 自动化必须可见、可控、可撤销

小妍可以主动建议，但不能在用户不知情时替用户发送、删除、覆盖或公开研究资产。记忆可查看、可编辑、可关闭、可删除；高影响动作始终需要确认。

### 2.5 模型升级不等于产品升级

更强模型只有在固定任务上产生可复现收益，并通过合适的提示词、上下文、工具、状态机和交互落到产品中，才算完成升级。

### 2.6 改进必须进入正确的结构边界

继续遵守 [`development-principles.md`](./development-principles.md)：页面只组合，领域能力进入 `features/<domain>/`，远程调用、文件系统、Tauri、副作用、节流和状态机逻辑进入 hook 或 service。不得以“模型生成更快”为理由继续扩张超大页面或超大组件。

## 3. 北极星体验与衡量方式

### 3.1 北极星体验

用户在间隔数天后重新打开一个研究主题，小妍能够：

1. 正确说明此前目标、已完成工作、关键证据和未解决问题；
2. 给出与当前阶段相符、可执行且可追溯的下一步；
3. 在用户确认后直接进入对应工作流；
4. 完成任务后沉淀必要资产和 checkpoint，供下次继续。

### 3.2 核心指标

指标按版本记录基线，不在缺少数据时伪造增长结论。

| 维度 | 指标 | 定义 | 首个目标 |
| --- | --- | --- | --- |
| 连续性 | 研究续接成功率 | 用户从主题总览或 checkpoint 发起续接后，无需重新解释背景即可进入有效下一步的比例 | 建立匿名、可关闭的本地基线 |
| 有效性 | 任务一次完成率 | 无需重试或大幅重写即可被用户接受的任务比例 | 按任务类型分别建立基线 |
| 纠错成本 | 用户纠正率 | 用户明确指出上下文、事实、格式或意图错误的任务占比 | 连续两个版本下降 |
| 可信度 | 证据覆盖率 | 应引用证据的结论中，具有可打开来源或本地资产关联的比例 | 核心科研任务优先覆盖 |
| 记忆质量 | 有效召回率 | 被召回的长期记忆中，用户保留或实际使用的比例 | 高于误召回率，且可解释 |
| 可恢复性 | 失败恢复率 | 超时、模型失败或工具失败后，可重试、续跑或保留部分结果的比例 | P0 流程全部具备恢复路径 |
| 效率 | 到达有效结果耗时 | 从发起任务到获得首个可用结果的时间 | 同质量前提下持续下降 |
| 安全 | 严重隐私事故数 | 未经授权持久化、上传或展示敏感内容 | 始终为 0 |

配套观察指标包括主动建议采纳率、checkpoint 续接点击率、工具调用成功率、模型成本和 P95 延迟。它们用于诊断，不单独作为成功标准。

### 3.3 反指标

以下变化出现时，即使核心指标上升也必须复核：

- 用户为了关闭错误记忆或无关建议而增加操作；
- 回答更长但证据密度下降；
- 自动任务变多但撤销、失败或误触发变多；
- 依赖更大上下文换取表面效果，导致隐私、成本或延迟明显恶化；
- 只在演示样例有效，真实研究主题无法复现。

## 4. “越用越好用”的五层能力

### L1：任务连续

- 会话、研究主题、论文、知识、实验、投稿和 checkpoint 有稳定关联；
- 用户离开后能从工作台续接，而不是重新描述背景；
- 失败任务保留目标、输入边界、已完成步骤和可重试点。

### L2：上下文准确

- 根据任务选择最小充分上下文，不把所有历史都塞给模型；
- 能区分用户原话、模型推断、外部来源和本地资产；
- 上下文过期、冲突或缺少来源时主动提示。

### L3：偏好适配

- 只学习用户明确表达或多次稳定出现的偏好；
- 区分全局偏好、研究主题偏好和单次任务要求；
- 用户可以查看“为什么这样回答”，并修正或删除相关偏好。

### L4：协作主动

- 基于 DDL、开放问题、实验阻塞和阅读计划提供适时建议；
- 每条建议说明触发原因、预期收益和所需动作；
- 默认建议而非代替执行，高影响动作必须确认。

### L5：系统自我改进

- 从脱敏反馈、失败类型和固定评测集中识别共性问题；
- 每次 Codex 升级都重新评估提示词、工具契约、上下文策略、状态机和 UI；
- 通过代码评审、测试和灰度发布改进，不允许运行时自行修改生产代码。

当前阶段的重点是夯实 L1、L2，并开始建立 L3 的可控偏好机制。L4、L5 依赖可靠的评测和隐私基础，不能提前用黑盒自动化替代。

## 5. 持续进化闭环

每一轮产品迭代统一走以下闭环：

```text
真实任务与反馈
    ↓
脱敏归类（连续性 / 事实 / 证据 / 工具 / 交互 / 性能 / 隐私）
    ↓
可复现样例与基线评测
    ↓
定位改进层（Prompt / Context / Tool / Runtime / UI / Data）
    ↓
小步代码改动 + 测试
    ↓
离线评测 + 人工科研任务验收
    ↓
灰度发布与指标观察
    ↓
更新本文、评测集和下一轮优先级
```

### 5.1 反馈来源

- 用户主动反馈：设置页反馈、Issue、访谈和可选的任务后评价；
- 产品信号：重试、停止、撤销、来源打开、结果复制、资产导入和 checkpoint 续接；
- 工程信号：模型错误、工具失败、超时、上下文截断、解析失败和崩溃；
- 评测信号：固定用例回归、隐私测试、性能测试和人工专家评审。

### 5.2 数据边界

- 默认不采集论文正文、聊天正文、截图内容、API Key、文件路径和未公开研究信息；
- 优先在本地计算聚合指标，仅在用户明确同意时上传脱敏结果；
- 反馈附件和诊断日志必须明确展示内容、用途和删除方式；
- 用于评测的真实案例必须先去标识化；无法可靠脱敏时使用合成案例；
- 每个新增信号必须记录用途、保留期、开关和删除路径。

## 6. Codex 模型升级后的强制流程

### 6.1 术语

- **Codex 开发模型升级**：用于阅读、规划、修改和验证本仓库的 Codex 模型或关键代理能力发生变化；
- **小妍运行模型升级**：用户在小妍内配置的主模型、视觉模型或任务模型发生变化。

本节主要约束 Codex 开发模型升级。运行模型升级也应复用评测门槛，但不强制修改仓库代码。

### 6.2 升级触发条件

满足任一条件即启动一次“模型进化迭代”：

- Codex 模型名称、主要版本或推理/工具能力升级；
- Codex 新增重要能力，例如更长上下文、视觉、浏览、并行代理或更可靠的工具调用；
- 同一模型的行为变化导致固定评测明显波动；
- 仓库决定采用新的 Codex 工作流、技能或插件作为默认开发能力。

### 6.3 八步升级流程

1. **登记模型指纹**

   记录日期、可见模型名/版本、关键能力、已知限制和执行环境。无法获得精确构建号时明确写“未知”，不得猜测。

2. **冻结升级前基线**

   在相同代码、配置、数据和评测用例上保存当前分数、失败样例、耗时和成本。没有旧模型可复跑时，至少保存最近一次可信结果。

3. **执行能力差异评测**

   新模型必须运行第 7 节的固定评测集。重点比较正确性、证据、工具选择、结构遵循、恢复能力、修改范围和测试质量。

4. **形成能力差异表**

   对每项能力标注 `提升 / 持平 / 退化 / 未知`，并给出样例证据。禁止仅凭发布说明判断产品收益。

5. **选择一个垂直改进切片**

   每次升级至少选择一个能被新能力实质改善的真实路径，例如“续接研究 → 检索证据 → 生成下一步 → 保存 checkpoint”。切片必须端到端可验收，不做无用户价值的模型名替换。

6. **同时迭代文档和代码**

   更新本文的版本、基线、优先级和迭代记录；提交对应的小妍代码、测试及必要的单功能文档。若评测未发现值得落地的代码收益，则暂缓采用该升级，而不是制造空改动。

7. **通过发布门槛**

   运行相关包 `type-check` 和测试；结构性或跨工作区修改按开发原则补跑 `pnpm type-check` 与 `pnpm lint`。高风险改动还需人工回归和隐私检查。

8. **灰度、观察与复盘**

   先对有限用户或受控环境开放，观察一个约定周期；将真实问题补入评测集，并在本文追加结论和下一步。

### 6.4 每轮必须交付的内容

- 本文的一条迭代记录；
- 一份模型能力差异与评测结果，可直接写入迭代记录；结果较长时再拆到 `docs/evolution-runs/`；
- 至少一个由评测证据支持的小妍代码改进及对应测试；
- 验证命令和结果；
- 回滚条件、未解决风险与下一轮候选项。

### 6.5 禁止事项

- 不因新模型“看起来更聪明”直接大范围重写；
- 不同时改模型、Prompt、工具、数据和 UI 后声称收益来自模型；
- 不删除失败样例来提高分数；
- 不把真实私密研究材料提交进评测集或仓库；
- 不用新增功能数量代替质量改进；
- 不在缺少评测证据时提高自动执行权限。

## 7. 固定评测集

评测集以可复现、贴近科研主流程为准。首版至少包含下列场景，每项保留正常、边界和失败恢复样例。

| 编号 | 场景 | 主要验证 |
| --- | --- | --- |
| E01 | 间隔多日后续接研究主题 | checkpoint 召回、目标一致性、下一步可执行性 |
| E02 | 基于本地论文回答事实问题 | 检索质量、引用准确性、不编造 |
| E03 | 精读论文并提取方法与局限 | 结构遵循、证据定位、未知项处理 |
| E04 | 从论文生成复现实验计划 | 依赖完整性、风险识别、与实验资产关联 |
| E05 | 根据证据辅助写作或改稿 | 论证边界、引用保持、用户文风约束 |
| E06 | 多意图任务的 Agent 与工具选择 | 路由准确性、最少充分工具、执行顺序 |
| E07 | 模型、网络或工具中途失败 | 部分结果保留、错误说明、重试与续跑 |
| E08 | 敏感文本、截图或受限应用输入 | 阻断、遮盖、确认、无意外持久化 |
| E09 | 用户纠正事实或偏好后再次请求 | 纠正是否生效、作用域是否正确、可撤销 |
| E10 | 桌面悬浮助手快速解读并导入资产 | 来源追溯、模型路由、导入结果与清理 |

### 7.1 评分标准

每个场景按 0—4 分评分：

- `0`：未完成或产生严重错误/隐私风险；
- `1`：部分输出，但无法用于真实任务；
- `2`：基本可用，需要明显人工纠正；
- `3`：可直接使用，仅需轻微调整；
- `4`：完成质量高，证据、交互和恢复路径均清晰。

同时单独记录以下硬指标：

- 事实与引用错误数；
- 不必要工具调用数；
- 未经授权的持久化或外发次数；
- 任务完成时间、Token/成本和重试次数；
- 修改代码时的越界文件数、测试通过率和未解释 diff。

### 7.2 升级准入门槛

在建立真实基线前，先使用以下相对门槛：

- E08 不得出现任何退化或严重问题；
- E01、E02、E06、E07 的平均分不得下降；
- 全集平均分应有可复现提升，或在质量不降的前提下降低成本/延迟；
- 不得出现单项下降超过 1 分而无明确缓解措施；
- 选中的垂直改进切片必须有自动测试和人工验收记录；
- 无法通过时保留旧流程，并把失败样例纳入下一轮。

## 8. 技术演进主线

### 8.1 评测与可观测性

目标：知道小妍为什么成功或失败，而不是只看最终文本。

- 为 Agent 运行记录模型角色、模型标识、Prompt/工具契约版本、上下文来源、路由结果、耗时和错误类型；
- 建立脱敏的任务事件模型与本地指标汇总；
- 建立固定评测夹具、模型适配器和可比较报告；
- 将高频真实失败转为回归测试。

### 8.2 研究上下文

目标：给任务最小充分、来源明确、时效正确的上下文。

- 统一研究主题、论文、知识、实验、投稿和 checkpoint 的上下文装配；
- 为每段上下文保留来源类型、资产 ID、更新时间和选择原因；
- 增加上下文预算、去重、冲突检测和过期提示；
- 把上下文策略留在 service/hook，不散落在页面或 Prompt 字符串中。

### 8.3 记忆与偏好

目标：用户纠正一次后，小妍在正确范围内持续改进。

- 将记忆分为事实、偏好、决策、开放问题和下一步；
- 增加作用域、置信度、来源、过期时间和撤销状态；
- 建立“候选记忆 → 用户确认或稳定证据 → 正式记忆”的晋升机制；
- 在召回时展示使用了哪些记忆以及原因；
- 对错误记忆提供一键纠正和删除。

### 8.4 Agent 与工具

目标：复杂任务选择正确能力，并能中断、恢复和复盘。

- 工具使用结构化输入输出和明确错误类型；
- 路由结果可解释，并有规则降级；
- 状态机支持停止、重试、局部续跑和幂等；
- 高影响工具按风险分级，权限与确认独立于模型判断；
- 将工具成功率和无效调用纳入评测。

### 8.5 交互与主动协作

目标：建议出现得及时，但不打扰、不越权。

- 工作台围绕“继续研究”而非模块导航组织；
- 结果提供来源、使用的上下文、可执行下一步和保存去向；
- 主动建议基于明确触发器，支持忽略、稍后和关闭同类建议；
- 对模型不确定性、失败和数据边界使用统一文案。

## 9. 分阶段路线图

### 阶段 A：建立可信基线（1—2 个迭代）

交付：

- 固化 E01—E10 的首版样例、评分表和运行方式；
- 为 Agent 运行补齐模型/策略/工具/耗时等必要元数据；
- 对现有反馈入口增加结构化问题分类设计；
- 记录连续性、工具失败和证据覆盖的首个本地基线；
- 完成第一次 Codex 模型进化迭代记录。

完成标准：

- 任意核心改动都能说明改善了哪个评测场景；
- 同一评测在相同环境可重复执行和比较；
- 不依赖上传用户正文即可定位主要失败类型。

### 阶段 B：让研究真正可续接（2—4 个迭代）

交付：

- 统一研究上下文装配和来源标记；
- 提升 checkpoint 的决策、开放问题和下一步质量；
- 工作台续接入口能够直接恢复任务和相关资产；
- 中断任务支持保留部分结果并从失败节点重试。

完成标准：

- E01、E07 达到稳定可用；
- 用户无需重复说明已保存的研究目标和最近决策；
- 所有 P0 任务存在可观察、可恢复的失败路径。

### 阶段 C：形成可控的个性化（3—5 个迭代）

交付：

- 偏好/事实/决策分层记忆；
- 记忆查看、纠正、删除、关闭和作用域控制；
- 任务结果中的“为何这样回答”说明；
- 纠正反馈进入候选记忆与回归样例。

完成标准：

- E09 稳定提升；
- 有效召回高于误召回，错误记忆可快速修复；
- 关闭记忆后不再产生隐式长期个性化。

### 阶段 D：适度主动与跨模块闭环（持续）

交付：

- 基于 DDL、实验阻塞、开放问题和阅读计划的可控建议；
- “建议 → 执行 → 资产 → checkpoint → 下次续接”闭环；
- 研究、写作、实验和投稿间的证据链完整；
- 持续运行 Codex 升级评测和灰度机制。

完成标准：

- 主动建议采纳率提升且关闭/忽略成本不增加；
- 核心科研结论具备来源或明确不确定性；
- 新模型升级不再依赖个人感觉决定。
